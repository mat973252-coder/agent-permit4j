# v0.4: outcome reconciliation

Status: implemented and locally verified on 2026-09-06; unreleased development
version `0.4.0-SNAPSHOT`. Authorized on 2026-09-06. Baseline: `be2ed00` (198 passing
tests). Working branch: `zjz/v0.4-outcome-reconciliation`.

## Outcome

An application can inspect an uncertain refund using a safe operation reference,
query authoritative downstream state, and record the resolution without making a
second payment. A timeout alone must never establish that payment did not happen.

## Delivery order and checks

1. **Failure fixture:** extend the controllable local payment simulator to preserve
   a payment even when its response or the following ledger commit is lost.
   Verify: reproduce the v0.3 recovery gap deterministically, with one payment and
   no automatic replay. Start with a failing acceptance test.
2. **Outcome contract:** derive the smallest result/reference API from that
   fixture. Distinguish confirmed success, confirmed failure, and uncertainty.
   Verify: an ambiguous transport exception remains uncertain; public views and
   audit contain no raw arguments, secrets, or execution capability.
3. **Reconciliation:** query the simulator by its stable operation identity and
   update the local record conditionally from authoritative evidence.
   Verify: repeated or concurrent reconciliation resolves once; it never invokes
   payment, and cannot attach another tenant's payment to the operation.
4. **Recovery demonstration:** rebuild the application services over retained
   fixture state and inspect the same uncertain operation.
   Verify: a successful downstream payment can be found after service restart,
   while an unavailable or inconclusive downstream query leaves it fenced.

Keep new production APIs driven by these tests. Use the existing dependency
direction; no framework or storage client enters core. Run narrow offline tests
for each slice and `.\mvnw.cmd -B -ntp verify` before completion.

## Implementation decisions

- Preserve existing decision outcomes and failed-result caches. A separate small
  execution-outcome value expresses NOT_STARTED, UNKNOWN, SUCCEEDED, or FAILED;
  executing a status query successfully does not prove that a refund succeeded.
- Give the backend preview a separate opaque operation reference before execution.
  It is neither an approval ID nor the pipeline idempotency key. Lookup and reconciliation
  require the trusted original principal, tenant, and environment. Possession of
  the reference alone grants no authority to execute or inspect a refund.
- Persist the refund proposal in the demo business database. Before payment,
  atomically reserve the order and move that proposal to UNKNOWN. Keep the
  reservation until authoritative success or rejection is recorded; a service
  restart or empty downstream query must not release it or resend payment.
- Store and reconcile refund balances in the same local transaction as the
  operation resolution. Keep domain-specific storage and payment handling in
  Playground; only the minimal outcome value belongs to the reusable execution
  module. Do not build a generic workflow or reconciliation repository without
  another concrete domain use case.
- Inject response/commit failure deterministically. The initial lost-response
  test first failed because the simulator lacked the fault seam, then passed,
  proving that payment can survive a local ledger rollback.

## Failure matrix

| Case | Required observation |
| --- | --- |
| Confirmed rejection before payment | Known failure, zero payment |
| Payment accepted but response lost | Uncertain locally, one payment, no replay |
| Payment accepted but ledger commit lost | Reconciliation recovers from downstream evidence |
| Downstream status unavailable or inconclusive | Remains uncertain; no automatic execution |
| Repeated/concurrent reconciliation | Same resolution; still one payment |
| Another tenant or mismatched operation | Denied; original operation unchanged |
| New application service instances | Retained operation remains inspectable |

## Adoption and subsequent choices

After the recovery proof, have an independent developer integrate three existing
Spring AI tools using the walkthrough. Record elapsed time, extra wiring, and
unsupported signatures; this has not been measured yet. Use that evidence to
prioritize DTO/proxy support or a gateway-facing adapter.

Gateway transport, OPA, Kafka, broad workflow orchestration, automatic retry of
uncertain writes, real payment integration, and publication are outside this
iteration. Distributed exactly-once is not an acceptance claim.

## Verification evidence

- Red/green: `RefundLostResponseTest` first failed because the fault-injection
  method was absent, then proved payment survived response loss and local rollback.
- Red/green: `RefundReconciliationAcceptanceTest` first failed because the outcome
  values and operation service were absent. The implementation then passed known
  rejection, lost response, owner isolation, unavailable evidence, service rebuild,
  and concurrent reconciliation cases.
- Red/green: `RefundWorkspaceRecoveryTest` first failed because the preview had no
  independent operation reference and workspace had no service-rebuild/query API.
  It now proves exact approval binding, safe UNKNOWN output, rebuilding over
  retained state, reconciliation without another payment, and immutable old snapshots.
- Additional fault coverage: `RefundReconciliationFaultTest` injects failure before
  and after the settlement commit, lost reservation acknowledgment before payment,
  and receipts for another reference or tenant. Uncertain operations remain fenced.
- Eight independent service/client instances race the same reference and dispatch
  one payment. Eight concurrent reconciliation callers apply one ledger transition.
- Full validation: `.\mvnw.cmd -B -ntp verify` passes all 12 modules with 212 tests,
  zero failures/errors/skips, including the CLI's normal and recovery scenarios.
  This adds 14 cases over v0.3. External Redis opt-in integration tests were not run.
- Narrow checks used Maven reactor selections with `-Dtest=Refund*Test` or the
  relevant individual test classes and `-Dsurefire.failIfNoSpecifiedTests=false`.
  `git diff --check` passes.
- Three independent read-only reviews checked the reservation/settlement
  transactions, final guarded integration, and documented guarantees/size limits.
  No blocking issue remained.

The delivered recovery proof rebuilds services over retained fixture state; it
does not kill the JVM or contact a real payment provider. Independent-adopter
measurement remains the next check, not a completed part of this technical proof.
