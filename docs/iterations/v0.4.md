# v0.4: outcome reconciliation

Status: planned, not implemented. Prepared on 2026-09-06 after the local v0.3
acceptance pass. Keep the order-refund example as the executable proof.

## Outcome

An application can inspect an uncertain refund using a safe operation reference,
query authoritative downstream state, and record the resolution without making a
second payment. A timeout alone must never establish that payment did not happen.

## Delivery order and checks

1. **Failure fixture:** extend the controllable local payment simulator to preserve
   a payment even when its response or the following ledger commit is lost.
   Verify: reproduce the v0.3 recovery gap deterministically, with one payment and
   no automatic replay. Start with a failing acceptance test.
2. **Outcome contract:** derive the smallest result/reference API from that
   fixture. Distinguish confirmed success, confirmed failure, and uncertainty.
   Verify: an ambiguous transport exception remains uncertain; public views and
   audit contain no raw arguments, secrets, or execution capability.
3. **Reconciliation:** query the simulator by its stable operation identity and
   update the local record conditionally from authoritative evidence.
   Verify: repeated or concurrent reconciliation resolves once; it never invokes
   payment, and cannot attach another tenant's payment to the operation.
4. **Recovery demonstration:** rebuild the application services over retained
   fixture state and inspect the same uncertain operation.
   Verify: a successful downstream payment can be found after service restart,
   while an unavailable or inconclusive downstream query leaves it fenced.

Keep new production APIs driven by these tests. Use the existing dependency
direction; no framework or storage client enters core. Run narrow offline tests
for each slice and `.\mvnw.cmd -B -ntp verify` before completion.

## Failure matrix

| Case | Required observation |
| --- | --- |
| Confirmed rejection before payment | Known failure, zero payment |
| Payment accepted but response lost | Uncertain locally, one payment, no replay |
| Payment accepted but ledger commit lost | Reconciliation recovers from downstream evidence |
| Downstream status unavailable or inconclusive | Remains uncertain; no automatic execution |
| Repeated/concurrent reconciliation | Same resolution; still one payment |
| Another tenant or mismatched operation | Denied; original operation unchanged |
| New application service instances | Retained operation remains inspectable |

## Adoption and subsequent choices

After the recovery proof, have an independent developer integrate three existing
Spring AI tools using the walkthrough. Record elapsed time, extra wiring, and
unsupported signatures; this has not been measured yet. Use that evidence to
prioritize DTO/proxy support or a gateway-facing adapter.

Gateway transport, OPA, Kafka, broad workflow orchestration, automatic retry of
uncertain writes, real payment integration, and publication are outside this
iteration. Distributed exactly-once is not an acceptance claim.
