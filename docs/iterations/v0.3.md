# v0.3: trusted business writes

Status: implemented and locally verified on 2026-09-06. Unreleased development
version: `0.3.0-SNAPSHOT`. Agreed direction: 2026-09-06.

## Outcome

A Java application can expose order lookup, refund preview, and refund execution as
guarded tools. A reviewer approves a concrete backend-built change. Only the
approved requester, tenant, amount, order version, and policy revision can execute
it. Concurrent retries produce one payment and one business-ledger change.

The example uses synthetic orders, a local H2 ledger, and an in-process payment
simulator. It never contacts a payment provider. Demo dependencies stay in the
Playground; core remains framework-free. Existing public APIs remain compatible.

## Completed delivery order

1. **Business slice:** prove the ledger transition and approval/retry boundaries
   against the existing pipeline before adding convenience APIs.
2. **Method integration:** use the example's actual needs to add explicit,
   deterministic registration of annotated methods. The original method executes
   only inside the idempotency owner, with normalized arguments and trusted context.
3. **Reviewed approval:** add a trusted approver authorization boundary and a
   retrievable decision record. Preserve old trusted-infrastructure APIs, but do not
   let them approve a request that requires an identified reviewer.
4. **Change contract:** retain a safe before/after preview; bind the amount,
   expected order version, and policy revision to the approved invocation. Enforce
   the resource condition in the database write, not only in preflight.
5. **Adoption proof:** document one command and the three-tool integration, run
   the full acceptance matrix, and review the final diff.

Each behavior starts with a failing executable test. Run the narrow reactor test
selection during development and `.\mvnw.cmd -B -ntp verify` before handoff.

## Acceptance matrix

| Case | Required observation |
| --- | --- |
| Order lookup and preview | No payment; preview describes a real local order |
| Refund without approval | Approval required; no ledger change or payment |
| Exact approved refund | Balance and version change; one payment |
| Same-key concurrent retries | Same output; one payment and one ledger change |
| Changed amount or policy revision | Old approval invalid; no new payment |
| Unauthorized, other-tenant, or self approval | Denied; no approval transition |
| Legacy approval of a reviewed request | Denied; no approval transition |
| Order changes after preflight | Conditional write rejects before payment |
| Known payment failure | Ledger transaction rolls back; no automatic retry |
| Duplicate tool registration | Startup failure instead of silent replacement |
| Method normalization | Business method receives the approved normalized values |
| Audit and review inspection | No execution and no raw sensitive arguments |

## Limits and subsequent work

The current pipeline rechecks authorization, risk, and approval before consulting
the result cache. Expired approval does not authorize access to a cached result.
Preserve that boundary in this iteration.

Redis and external business systems are not one transaction. Unknown results,
downstream reconciliation, retention, and partitioning need a separate iteration;
v0.3 does not claim unconditional exactly-once delivery. Do not add automatic
retry, lease takeover, a general workflow engine, or real payment credentials.

MCP/gateway integration can later expose the same protected business boundary.
OPA, Kafka, approval-channel integrations, and broad DTO support follow actual
adopter needs. No publication, push, or production deployment is part of this
implementation iteration.

## Evidence

- Baseline: commit `c33911c`; full Maven Wrapper verify passed with 181 tests in
  the review preceding this iteration. Real Redis integration tests are opt-in.
- Working branch: `zjz/v0.3-trusted-business-actions`.
- New behavior was introduced test-first: the ledger, guarded-method factory,
  identified-review APIs/schema, and workspace acceptance tests initially failed
  because their production types or resources were absent. Each slice then passed
  its narrow Maven reactor test selection.
- `RefundLedgerAcceptanceTest` proves actual row changes, concurrent retries,
  version/tenant/balance conditions, known payment rejection rollback, and an
  order update injected during approval verification before execution.
- `GuardedToolMethodsAcceptanceTest` proves guarded method dispatch, normalized
  arguments, trusted identity, immutable registration, and duplicate-name rejection.
- `ReviewedApprovalAcceptanceTest` runs against both in-memory and JDBC services:
  unauthorized/cross-tenant/self review, legacy bypass, original decision
  retention, and changed amount/policy fingerprint rejection.
- `JdbcApprovalReviewTest` proves first-review retention across JDBC instances and
  rollback when the decision record cannot be written.
- `RefundWorkspaceAcceptanceTest` covers the three-tool flow, parameter/policy
  changes, stale orders, missing inputs, eight concurrent callback retries, and
  denial when a consumed approval is reused with another idempotency key.
- Final command: `.\mvnw.cmd -B -ntp verify`. All 12 reactor modules pass;
  198 tests, zero failures/errors/skips. Both CLI demonstrations run successfully.
  This is 17 added test cases over the baseline. External Redis integration tests
  remain opt-in and were not run.
- Two independent read-only reviews examined approval transactions and method /
  business execution. No actionable security defect remained. The reported missing
  number-input suspicion was disproved by an executable callback acceptance test;
  no production change was needed for it.
- `git diff --check` passes. No real payment, release, push, or deployment was run.

## Next iteration

Follow [v0.4 outcome reconciliation](v0.4.md): prove the payment-success / lost-receipt
case before adding a reusable outcome contract. The present example does not yet
recover that case. Independent adopter integration time also remains unmeasured.
